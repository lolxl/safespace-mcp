## Problem Statement

The user (owner: themselves) holds several Google accounts at once (personal + work + side-project / client accounts) and wants to operate Gmail and Google Drive with AI through Claude Code or another MCP client. 7+ open-source multi-account Gmail MCP servers already exist (`taylorwilsdon/google_workspace_mcp`, `dmorrill/gmail-mcp-multi`, `3vening/gmail-mcp`, …), but none of them simultaneously clears the user's acceptance bar on three specific security dimensions — hence the decision to build one.

## What Makes This Cool

- **Not yet another multi-account MCP, but a security-first design**: three concrete security pillars (minimum OAuth scope, local keychain tokens, MCP-layer untrusted-content tagging) as the product's spine
- **Code small enough for the user to personally audit every line**: target 400 LoC / hard cap 600 LoC. Being readable in 30 minutes is **itself a design goal**
- **Lateral architecture**: instead of rewriting 85 tools, wrap Google's official remote MCP endpoint (if it exists — see Step 0). Future Google tool additions come for free, while the trust boundary stays local
- **Active-account as a first-class primitive**: the last-used account automatically becomes active unless explicitly specified

## Constraints

- Single developer (the user), weekend-project cadence
- Platform: macOS first (Keychain integration); Linux / Windows support is not a v1 goal
- Primary MCP client: Claude Code; secondary: Claude Desktop, other MCP clients
- No data may be sent to any third-party telemetry / analytics endpoint
- Tokens must never be written to disk in plaintext

## Premises (user-agreed)

- **P1. The real reason for building it ourselves is security posture**, not NIH and not mere learning. Three facets:
  - (a) **Minimum OAuth scope**
  - (b) **Local token storage** (macOS Keychain)
  - (c) **MCP-layer untrusted-content tagging + basic hygiene** (see the honest reframing in the sanitize section below)
- **P2. Primary user = self. Primary client = Claude Code**
- **P3. Scope boundary = only the 5 tools actually used** (v1)
- **P4. Code small enough to hand-audit (400 target / 600 hard cap)**
- **P5. Multi-account is a first-class primitive**
- **P6. The sanitize pipeline's security guarantee comes primarily from the `<untrusted-source>` wrapper + LLM training; pattern detection is only defense-in-depth**
- **P7. Release strategy = personal use first**

## Approaches Considered

### Approach A: "5-Tool Keychain MCP" (Minimal Viable)
Single-file TypeScript MCP server, 5 tools, Keychain tokens, no injection tagging. ~300 LoC.
- Completeness: 5/10 — misses P1(c); rejected

### Approach B: "SafeSpace MCP" (Ideal Architecture)
Three-layer architecture, ~800 LoC, all three pillars + a sanitize pipeline with 80%+ test coverage.
- Completeness: 9/10
- Recommended to the user but not selected

### Approach C: "Local Security Proxy" (**selected**)
A local proxy MCP server wrapping Google's official remote MCP endpoint. The proxy layer owns keychain tokens, scope minimization, untrusted-content tagging, and the tool-whitelist filter.
- Completeness: 6/10 — see "Completeness Gap" below for why the 3-point gap exists and how it is absorbed

## Recommended Approach

**Realist repositioning (required by the round-2 review):** Google's official Gmail/Drive remote MCP endpoint had **no verifiable public documentation** as of 2026-04 (BigQuery MCP was preview; Gmail/Drive unconfirmed). Given that fact:

- **Default path = Approach B-lite (direct `googleapis` calls)**, LoC estimate ~600 (the 600 hard cap is hereby relaxed to 700 for B-lite specifically)
- **Upgrade path = Approach C (proxy the Google endpoint)** — switch over if the Step 0 spike finds a GA Gmail/Drive remote MCP

**The Auth / Tool Filter / Scope Guard / Sanitize Pipeline are nearly identical on both paths** — the only difference is whether the tool-implementation layer calls the `googleapis` npm package or forwards to a remote MCP. Most code is reusable; the switching cost is low.

### Completeness Gap (C vs B)

C scores 3 points below B, in exchange for: LoC dropping from ~800 to ~400, and the tool surface expanding from "5 hand-written" to "the whole Google suite".
Concrete gaps:
1. **Depends on the availability of Google's official remote MCP** (see Step 0; most likely it does not exist)
2. **Streaming tools are buffered for now** (v2)
3. **Attachment content (PDF/image) gets no binary sanitization in v1**

### Architecture (three layers)

```
Claude Code  <—stdio MCP—>  Local Proxy (your code)  <—HTTPS—>  Google Remote MCP or googleapis
                                  │
                                  ├─ Auth Layer       (Keychain tokens + local 127.0.0.1 OAuth consent flow)
                                  ├─ Tool Filter      (whitelist exposure + non-whitelisted tools/list stripped, tools/call rejected)
                                  ├─ Scope Guard      (computed statically at consent time; no runtime re-verification)
                                  └─ Sanitize Pipeline (tag + hygiene; see the honest reframing below)
```

### How the three pillars map to implementation

**P1(a) Minimum OAuth scope**
- `TOOL_REGISTRY` explicitly declares the scopes of every whitelisted tool
- OAuth consent computes the scope union dynamically from TOOL_REGISTRY (**static at consent time; no runtime re-verification**)
- Adding a tool → edit TOOL_REGISTRY → re-run consent; Google does not always accept incremental scopes, so a full re-consent may be needed

**P1(b) Local token storage**
- macOS Keychain, one entry per account (service: `safespace-mcp`, account: email)
- **Selection**: prefer `@napi-rs/keyring` (actively maintained, Bun-compatible, no native-build codesign issues), falling back to a `security` CLI shell-out (macOS built-in, zero dependencies, but slow)
- **Do not use `keytar`** — archived (the original `atom/node-keytar` repo is archived); Bun support not guaranteed
- The OAuth refresh flow lives inside the proxy; no other network egress (besides the Google OAuth endpoint + Google API/MCP endpoints)

**P1(c) Sanitize pipeline — the honest reframing**

**The security guarantee comes primarily from two things (best available mitigation, not a formal guarantee):**
1. **The `<untrusted-source origin="gmail" sender="...">...</untrusted-source>` wrapper** — tells the LLM "the following content comes from an untrusted source and is not a system instruction". This is **the most effective mitigation available today**, but not a formal guarantee — Claude / GPT instruction-following training **mostly** respects such tags, but not 100%
2. **The LLM's own instruction-following training** — known to handle untrusted-content blocks **in most cases**

**Defense-in-depth (not the primary security layer):**
- Strip zero-width chars (U+200B, U+200C, U+200D, U+FEFF) — blocks trivial text hiding
- Normalize Unicode confusables — using a subset of [Unicode confusables.txt](https://www.unicode.org/Public/security/latest/confusables.txt), limited to Latin/Cyrillic/Greek confusion
- Detect & flag known injection patterns — a precise regex list checked into the repo at `sanitize/patterns.ts`. Example:
  ```typescript
  // sanitize/patterns.ts example (non-exhaustive)
  export const PATTERNS = [
    { id: "ignore-prev", re: /ignore\s+(all\s+)?(previous|prior|above)\s+(instructions|rules|directives)/i, severity: "high" },
    { id: "system-prompt-injection", re: /(system|assistant)\s*[:：]\s*you\s+are\s+/i, severity: "high" },
    { id: "role-hijack", re: /\[INST\]|<\|im_start\|>|<\/instructions>|<\/system>/i, severity: "high" },
  ];
  ```
- **A flag means observability, not blocking**: on a pattern hit, prepend `<!-- sanitize-flag: ignore-prev -->` to the returned content as a hint to the LLM, but still return the content
- Truncate bodies > 50KB and note the truncation
- **Drive file hard cap: v1 refuses to download files >5MB** (prevents a Gmail-oriented design from accidentally becoming a big-file download channel — RAM-hungry and of limited sanitize value)

**Explicitly NOT done in v1 (not a v1 security promise):**
- ❌ No sanitization of attachment binary content (PDF / image text / embedded instructions) — flagged as a known gap
- ❌ No defense against translated instructions, obfuscated phrasing, or steganography — pattern matching cannot stop a motivated attacker
- ❌ No ML-based classifier (v2 could adopt gstack v1.5.0.0's 22MB TestSavantAI)

**Fail-closed policy**: if `sanitize()` throws on any content → the whole tool call fails. Return the standard MCP error:
```json
{ "code": -32000, "message": "sanitize_failed", "data": { "tool": "gmail_get_message", "reason": "malformed_content" } }
```
The raw content is **not** returned to the LLM (not even wrapped in the untrusted wrapper).

### Default tool whitelist (v1)

| Tool | Scope | Notes |
|------|-------|------|
| `gmail_search` | `gmail.readonly` | optional `include_snippets: boolean` (Issue 9A) → when true, fan out to fetch the first 5 messages' snippet+subject+from via Promise.all |
| `gmail_get_message` | `gmail.readonly` | |
| `gmail_send` | `gmail.send` | |
| `drive_search` | `drive.readonly` | |
| `drive_get_file_content` | `drive.readonly` | not `drive.file` (which can only read app-created files) |

**Additional account-management tools**:
- `account_list()` — list authorized accounts. **Enumeration mechanism**: query the Keychain filtered by service name `safespace-mcp`; macOS has no official keychain-list API → either parse `security dump-keychain | grep -A2 safespace-mcp`, or maintain a JSON index `~/.config/safespace/accounts.json` (storing only the email list, never tokens) — the latter chosen as the v1 route: simple and predictable
- `account_switch(email)` — switch the active account
- `account_revoke(email)` — **execution order = call Google revoke first → on success delete the Keychain + index entry**. If Google revoke returns non-200 (network error / already revoked) → still delete the local Keychain entry and return a warning to the LLM about the inconsistent state; the user then confirms manually at myaccount.google.com

**`account_id` argument rule**: every non-account-management tool optionally takes an `account_id` argument (type: email string); when omitted, `lastUsedAccount` is used. `account_switch` / `account_list` / `account_revoke` themselves do not accept it.

### Concurrency & Crash Safety (Issue 1A, 2A)

**Atomic write for `accounts.json`**:
- Every modification of `~/.config/safespace/accounts.json` = write to `.tmp` → `fs.rename(tmp, final)`
- POSIX `rename` is atomic; a crash mid-write cannot leave corrupt JSON
- On startup, if `accounts.json` is missing or fails JSON parse → rebuild via Keychain enumeration + a warning log

**Per-account refresh mutex**:
```typescript
// auth/refresh.ts
const refreshInFlight = new Map<string /* email */, Promise<TokenSet>>();

export async function refreshAccessToken(email: string): Promise<TokenSet> {
  let pending = refreshInFlight.get(email);
  if (pending) return pending;
  pending = doRefresh(email).finally(() => refreshInFlight.delete(email));
  refreshInFlight.set(email, pending);
  return pending;
}
```
- Parallel tool calls on the same account trigger only one refresh HTTP request
- If Google rotates the refresh_token → the new refresh_token is written back to the Keychain before returning (atomic set via `@napi-rs/keyring`)

### Runtime Audit Log (Issue 3A)

- Path: `~/.config/safespace/audit.jsonl`
- Append-only JSONL, one line each:
  ```json
  { "ts": "2026-04-22T07:15:00Z", "tool": "gmail_search", "account": "me@work.com",
    "args_hash": "sha256:abc...", "status": "ok", "duration_ms": 142 }
  ```
- **No tokens, no email content, no raw query strings** (args are hashed only — replay verification stays possible without leakage)
- CLI: `safespace audit --last 24h` | `safespace audit --account me@work.com --last 7d`
- Audit write failure (disk full) → log to stderr, do not abort the tool call (best-effort observability)

### withToolContext Middleware (Issue 6A)

```typescript
// tools/with-context.ts
export async function withToolContext<A, R>(
  toolName: string,
  args: A & { account_id?: string },
  fn: (ctx: ToolContext, args: A) => Promise<R>
): Promise<R> {
  // 1. resolve account (args.account_id or lastUsedAccount)
  // 2. get access token (refresh via mutex if needed)
  // 3. audit log: started
  // 4. call fn(), catch → map via errors.ts
  // 5. sanitize result
  // 6. audit log: completed + duration
  // 7. update lastUsedAccount
  // returns: sanitized result or throws MCP error
}
```

The 5 tool handlers contain only the Google API call logic (5–10 lines each); all 6 cross-cutting concerns live in the middleware.

### MCP Error Code Table (Issue 5A)

Every error uses the JSON-RPC standard shape `{ code, message, data: { reason, recovery? } }`:

| Code | Message | When | Recovery hint (for Claude to relay) |
|------|---------|-----|---------------------------------|
| -32000 | `sanitize_failed` | sanitize threw | "Content processing failed, possibly an unusual format. Try a different search query." |
| -32001 | `tool_not_found` | non-whitelisted tool called | "This tool is not enabled; check the whitelist." |
| -32002 | `keychain_locked` | macOS Keychain not unlocked | "The macOS Keychain is locked; unlock it and retry." |
| -32003 | `account_not_found` | the given account_id is not authorized | "That account is not authorized yet; run `safespace consent <email>`." |
| -32004 | `scope_mismatch` | the tool needs scopes beyond what the account granted | "The tool needs new permissions; run `safespace consent <email> --re-auth`." |
| -32005 | `rate_limited` | Google 429 exhausted | data.retry_after_sec; "API rate limit reached; retry in N seconds." |
| -32006 | `refresh_token_invalid` | Google rejected the refresh | "Authorization expired or revoked; re-run `safespace consent <email>`." |

### Active-account mechanism
- The proxy keeps `lastUsedAccount` state (in-memory)
- Every tool call optionally takes `account_id`; when omitted, `lastUsedAccount` is used
- **Restart semantics**: `lastUsedAccount` does **not** persist; after a proxy restart it resets to **the first authorized account** (in Keychain order). Reason: simpler state, no file on disk

### Tool Whitelist Filter behavior
- In the `tools/list` response: non-whitelisted tools are stripped; Claude only sees the whitelist
- If `tools/call` receives a non-whitelisted tool name → return an error; never forward to Google

## Edge Cases & Failure Modes (reviewer findings)

| Scenario | v1 behavior |
|------|--------|
| Access token expired | The proxy auto-refreshes; if the refresh token is also invalid → clear the Keychain entry and return an error asking to re-run `safespace consent <email>` |
| Refresh-token rotation (Google sometimes returns a new refresh token) | The proxy **must overwrite** the existing Keychain entry with the new refresh token from Google's response; the old one is immediately invalid |
| Token revoked on Google's side | The next API call returns 401 → same path as an expired access token |
| Keychain locked (fresh boot, not yet unlocked) | Tool calls fail closed with MCP error `keychain_locked`; the user unlocks the Keychain and retries |
| Google silently grants broader scopes at re-consent | On receiving the token response, the proxy compares the actual granted_scopes against the TOOL_REGISTRY expectation; if **actual ⊋ expected** (excess) → log a warning but accept the token (Google policy); if **actual ⊊ expected** (shortfall) → reject the token, clear the entry, require re-consent |
| Are tool descriptions/schemas from the Google MCP forwarded verbatim? | **Not in v1** — the Tool Filter serves the descriptions/schemas hard-coded in the proxy's local TOOL_REGISTRY (prevents a Google-side description change from becoming a prompt-injection vector) |
| Revoking a single account | `account_revoke` deletes the Keychain entry + POSTs to Google `/oauth2/revoke` |
| Rate limit (429) | Exponential backoff: 1s / 2s / 4s (max 3 retries), then forward the error to Claude |
| Multi-device | **v1 is single-device**; other devices re-run consent (the Keychain doesn't cross machines; cross-device token sync only if ever needed) |
| Existing tokens when TOOL_REGISTRY scopes change | On startup the proxy compares the granted scopes recorded in the Keychain against the current TOOL_REGISTRY union; on mismatch → list the affected accounts and prompt `safespace consent <email> --re-auth` |
| Sanitize throws on malformed content | **Fail-closed**: the whole tool call errors out; the LLM sees no response |
| Google MCP streaming response | v1 buffers end-to-end (sanitize after fully received); streaming is a v2 concern |
| Google rejects incremental scope | The proxy instructs the user to do a full re-consent (the Google consent screen shows the delta automatically) |

## A0. Architecture pivot: gws subprocess (replaces Approach B-lite / C)

1. `args.account_id` (per-call override)
2. In-memory `lastUsedAccount` (set by any successful tool call this process)

## Sanitize: input-side defenses (extends original output-only design)

Original §Pillar P1(c) described **output-side** sanitize (`<untrusted-source>` wrap + confusable + zero-width strip). Step 5.9 added **input-side** defenses on `gmail_send`:

- CR / LF / NUL / U+0085 (NEL) / U+2028 (LINE SEPARATOR) / U+2029 (PARAGRAPH SEPARATOR) — rejected in `to`, `subject`, AND `ctx.email` (defense-in-depth on the From line)
- Subject restricted to printable US-ASCII (RFC 2822 §3.2.3) — v1 defers MIME RFC 2047 encoded-word
- Recipient count cap = 10 (anti-prompt-injection)
- Body cap = 1 MB (Gmail hard limit is 25 MB; we cap locally for argv sanity)

The asymmetry is intentional: read-side sanitize cannot reject (would mid-stream a tool response); write-side validation throws and aborts the call.

## Audit JSONL — concrete schema (Step 5.8, PR #15)

`~/.config/safespace/audit.jsonl`, mode `0o600`, parent dir `0o700`. One JSON object per line:

```json
{"ts":"2026-05-15T10:23:45.123Z","tool":"gmail_search","account_hash":"sha256:abc...","args_hash":"sha256:def...","status":"ok","latency_ms":412}
```

Fields:
- `ts` — ISO-8601 UTC.
- `tool` — registry name.
- `account_hash` — `sha256(email)` (first 16 hex chars). Never the raw email.
- `args_hash` — `sha256(JSON.stringify(args))`. Never raw args.
- `status` — `"ok"` | `"error:<errorName>"`.
- `latency_ms` — integer.

Append-only via POSIX `appendFile`. For lines ≤ 4 KB (PIPE_BUF), concurrent appends from the same process are atomic. Cross-process locking is NOT used (v1 single-user; race tolerance documented in Reviewer Concerns).

## Post-v1 Addendum — `--read-only` consent (2026-05-15)

`safespace consent <email> --read-only` requests only `gmail.readonly` + `drive.readonly` (drops `gmail.send`). Used by `scripts/setup-profiles.sh` for read-profile consents so accounts never loaded into the send profile (e.g. procurement) end up with refresh tokens that Google itself will refuse `users.messages.send` on.

This is **defense in depth on top of** the existing `SAFESPACE_ENABLE_SEND` process-global kill-switch (Plan D3). The two layers are independent:

| Layer | Where enforced | Failure mode |
|-------|----------------|--------------|
| `SAFESPACE_ENABLE_SEND=1` gate | Local, in `gmailSend()` handler | Throws `send_disabled` (MCPError -32009) before any token use |
| `--read-only` granted scope | Remote, at Google's API | Returns 403 insufficient_scope; we map to upstream error |

A misconfig that loads the wrong env file or a future bug that softens the local gate still cannot turn a `--read-only`-granted token into a send-capable one without re-running `consent` without the flag and clicking Allow again at Google's OAuth screen.

Implementation:
- `src/auth/consent.ts`: adds `V1_READONLY_SCOPES` (filter out `gmail.send` from `V1_SCOPES`); `ConsentOptions.readOnly` switches both the requested-scope list AND the post-grant required-scope check.
- `src/cli.ts`: parses `--read-only` flag.
- `scripts/setup-profiles.sh`: passes `--read-only` for all READ profile consents.
- Tests: 4 new in `src/auth/consent.test.ts` verifying the scope set is correctly minimized.

## v1.2 Addendum — Drive sharing (2026-05-16)

Adds two new MCP tools for Drive permission management: **`drive_share_file`** (write — create permission) and **`drive_unshare_file`** (recovery — delete permission). After v1.2 the send profile carries `https://www.googleapis.com/auth/drive` (full) instead of `drive.readonly`; read profile unchanged. Total: **9 MCP tools** (v1's 5 + v1.1's 2 + v1.2's 2). 347/347 tests pass at the ship of PR-4.

### New tools

| Tool | Type | Required scope | Defense layers |
|---|---|---|---|
| `drive_share_file` | WRITE | `drive` | 7 (see below) |
| `drive_unshare_file` | RECOVERY | `drive` | 2 (file_id regex + target_email validation) — deliberately light so brakes always work |

### Scope upgrade

`V1_SCOPES`: `drive.readonly` → `drive` (full). Rationale (sec-rev v1.2 PR-1 Q1):
- `drive.file` is **insufficient** — only grants access to files created or opened by our app; users want to share arbitrary files referenced by id.
- `drive.metadata.readonly` is **insufficient** — read-only metadata, no permission-write.
- `drive` is the narrowest scope that permits `permissions.create` / `permissions.delete` on arbitrary files.

Read profile keeps `drive.readonly` to preserve the **external-broadcast defense** ("procurement account physically cannot let data escape externally"). After v1.2:
- Read profile = `gmail.readonly + gmail.labels + gmail.modify + drive.readonly` — internal mutations only.
- Send profile = read profile + `gmail.send + drive` — can broadcast externally.

The line stays "can data escape to external parties?" — both profiles write; only one can broadcast.

### 7-layer defense (`drive_share_file`)

| # | Layer | Implementation |
|---|---|---|
| 1 | Kill switch | `SAFESPACE_ENABLE_DRIVE_SHARE=1`, default off. Parallel to `SAFESPACE_ENABLE_SEND` / `SAFESPACE_ENABLE_MODIFY`. |
| 2 | Type-aware expiration | `share_type=user` → 1-365 days mandatory (Google API rejects expiration on `anyone` permissions; we pre-reject for clearer error). `share_type=anyone` → must omit. |
| 3 | Single file per call | `file_id` is a string, not an array. No batch. |
| 4 | **Owner allowlist** (sec-rev H2) | `SAFESPACE_DRIVE_SHARE_ALLOWED_OWNERS` env var. Empty = nothing can be shared (fail-closed). Owner-lookup failure (network / 403 / timeout) also fails closed — we do not fall through on uncertainty. |
| 5 | File-id regex | `^[a-zA-Z0-9_-]{20,}$` rejects URL paste and obvious garbage. |
| 6 | Role allowlist + param hardcoding | Only `reader` / `commenter` accepted at validation. `writer` / `owner` / `organizer` / `fileOrganizer` rejected. `transferOwnership` / `pendingOwner` NEVER passed to gws (omitted, not just set to false). |
| 7 | Audit forensic JSONL | `auditShareEvent` writes one line per successful call: `{event: "share_forensic", file_id, share_type, role, target_email_hash, expiration_iso, granted_permission_id}`. Hash uses HMAC-SHA256 with an install-time random salt at `${configDir}/audit-salt` (sec-rev Q6). Full 32-byte digest hex-encoded — NOT truncated. |

### Recovery path (`drive_unshare_file`)

Deliberately lighter:
- **NO kill switch** — recovery should always work; brakes always work.
- **NO owner allowlist** — REMOVING access cannot leak data.
- Audit logs every delete (same `auditShareEvent` helper, `tool: "drive_unshare_file"`).

Internal flow: `permissions.list` (pageSize=100) → match by `(share_type, target_email)` tuple → `permissions.delete`. Case-insensitive email match (Gmail canonicalizes `user@gmail.com` == `User@gmail.com`). Files with >100 user permissions fall back to Drive web UI — documented limit.

### Scope hierarchy (sec-rev gap caught during PR-1)

Google's OAuth server returns the literal granted scope string. Granting `drive` does **not** auto-include `drive.readonly` in the granted set. Without hierarchy awareness, after a send profile re-consents to v1.2, every `drive_search` call (which declares `requiredScopes: [drive.readonly]`) would falsely fail `scope_mismatch`.

PR-1 added `SCOPE_HIERARCHY` in `with-context.ts` + `scopeSatisfies(granted, required)` helper. Encoded one-direction only: broader granted scope covers narrower required scope. Narrower granted scope NEVER covers broader required scope. Currently only encodes `drive.readonly` covered by `drive` (and itself).

### Risks NOT mitigated

- **Cached / mirrored content from a previously-leaked `anyone` link.** Once a public link is created and accessed, content can be archived / forwarded / cached. `drive_unshare_file` revokes future access via the permission, but cached / mirrored copies elsewhere remain accessible. There is no technical fix at this layer — operational discipline (the kill switch + allowlist + role limit + expiration on `user` permissions) is what reduces the chance of a leak in the first place.
- **DoS via wholesale unshare.** An attacker with MCP access could unshare every permission on critical files (denial of service, not data leak). v1.2 threat model is single-user self-use; out of scope.

## v2.0 Addendum — Tier system + single-profile collapse (2026-05-17)

The largest architectural shift since the gws-subprocess pivot (Step 5 A0). v2.0 retires the v1.x **two-profile structural defense** (procurement-account-physically-cannot-send via `safespace-read/` with `--read-only` consent + `SAFESPACE_ENABLE_SEND` kill switch in `safespace-send/`) and replaces it with two coordinated mechanisms:

1. **Tier-based tool exposure** at the MCP `tools/list` boundary (`SAFESPACE_TIER=read|write|share`), and
2. **Claude Code's per-call approve UI** (the user can deny any specific tool call interactively).

Total: still 9 MCP tools, but a single OAuth scope set per account and a single MCP server. **367/367 tests pass** at the ship of PR-4.

### Why we changed

v1.x's two-profile model worked but had three accumulating costs:

- **Every new write capability needed a new kill-switch env var** + the consequent docs / wizard / tests. By v1.2 we had `SAFESPACE_ENABLE_SEND`, `SAFESPACE_ENABLE_MODIFY`, `SAFESPACE_ENABLE_DRIVE_SHARE`, plus the v1.2 `SAFESPACE_DRIVE_SHARE_ALLOWED_OWNERS` allowlist. Cognitive load was outpacing the security gain.
- **The "procurement account can't send" defense was already largely operational, not structural**. Keychain entries are keyed by email under a single global `safespace-mcp` service name — both profiles already shared the same Keychain entries. The "physical incapability" was actually "the read profile's accounts.json doesn't list that account, plus the OAuth scope set lacks gmail.send". The first part is a use-pattern, not a structural barrier.
- **Claude Code grew per-call approve UI** in early 2026. That's now the right place to ask "is this specific send OK?" — and it's the only place that has the full call context (the prompt, the args, the conversation history).

The v2.0 redesign trades **structural lock** for **explicit user awareness per call** + **process-wide tier gating** + **use-pattern advice** ("don't load high-risk accounts at tier=write"). The forensic surface (audit.jsonl with HMAC-SHA256 target email hashing) is unchanged.

### Tier semantics

`SAFESPACE_TIER` is monotonic. Each level exposes a superset of the prior:

| Tier | Tools advertised |
|---|---|
| `read` (default) | `gmail_search`, `gmail_get_message`, `gmail_list_labels`, `drive_search`, `drive_get_file_content`, `drive_unshare_file` |
| `write` | `read` + `gmail_send`, `gmail_modify_message`, `drive_share_file` (with handler-level `share_type=user` requirement) |
| `share` | `write` + `drive_share_file` with `share_type=anyone` permitted |

The proxy reads `SAFESPACE_TIER` once at startup and filters `tools/list` permanently. No per-call escalation. Changing tier requires editing `.env` and restarting Claude Code. Rationale (sec-rev v2.0 PR-1): a tool that the MCP never advertises cannot be invoked, even if Claude is prompt-injected — strictly better than a runtime check that depends on Claude not being persuaded.

**`drive_unshare_file` is exposed at every tier** (including `read`). It is a recovery tool — revoking access cannot leak data, and brakes should always work even when other capabilities are off.

**Legacy-flag bridge** (`src/tier.ts`, v1.0 only): originally, if `SAFESPACE_TIER` was unset but any of `SAFESPACE_ENABLE_{SEND,MODIFY,DRIVE_SHARE}` was set, the tier was auto-derived with a one-shot stderr deprecation warning. **Removed in v1.1.0** (the polish PR) per architect review — Option B (hard-fail) chosen over silent default-to-read because silent capability loss is the only outcome with an actually dangerous failure mode for upgraders. Current v1.1.0 behavior: legacy-flag-only env (without `SAFESPACE_TIER`) throws at proxy startup with a migration-doc error message pointing at `safespace migrate-v2` and the `SAFESPACE_TIER` setting.

### `migrate-v2` design

The data-merge tool's design is the new high-risk surface in v2.0; sec-rev produced 12 findings. Summary:

- **File lock with 30-min TTL** at `${CLAUDE_PLUGIN_DATA}/.migrate-v2.lock` (longer than `consent.ts`'s 10-min — migration can take minutes on large audit files). PID + mtime stale-lock recovery, mirrors `consent.ts` `acquireConsentLock`.
- **Stranded staging cleanup inside the lock** (H-NEW-1): `fs.rm safespace.tmp/` runs after `acquireMigrationLock`, not before. While another process holds the lock, its staging dir is owned (not stranded) and must not be blown away.
- **Pre-flight refusals**: refuse if `safespace/accounts.json` exists with data; refuse if any source `audit.jsonl` was modified within 60s (proxy may still hold an open fd; renaming the source dir mid-write would silently lose append-only writes); refuse on salt mismatch unless `--force-salt-mismatch`.
- **Accounts merge**: dedup by email, union scopes (sorted), earliest `added_at`, latest `last_used_at`. The schema bump v1 → v2 from PR-2b-1 is in-place: reader accepts both, writer always emits v2.
- **Audit merge (NO sort)**: per-source append order is preserved, separated by `{event:"migration_boundary", source, migrated_at, note}` JSONL records. Sec-rev H1 rationale: sorting by `ts` lets a crafted future/past entry sort into the wrong place, silently corrupting forensic chronology — the original file boundary is semantically ground truth.
- **`.env` + `audit-salt` copy**: prefer send-profile sources (drive-full = primary in v1.x), fall back to read. `.env` content is never included in error messages (C1 canary test asserts `SECRET-CANARY-DO-NOT-LEAK` never appears). `content` variable nulled after write to narrow the in-memory plaintext window.
- **`.env` `SAFESPACE_TIER` auto-derivation** (added post-v1.1, the DX patch for the legacy-flag hard-fail): if the copied `.env` contains uncommented `SAFESPACE_ENABLE_{DRIVE_SHARE,SEND,MODIFY}=1` AND no explicit `SAFESPACE_TIER=` line, migrate-v2 rewrites it: comment out the legacy flags, append `SAFESPACE_TIER=<derived>`. Precedence: `DRIVE_SHARE→share`, `SEND|MODIFY→write`. Without this, a clean v1.x → v2.0 migration leaves the proxy in startup hard-fail. Derivation lives in `src/tier.ts` (`deriveTierFromLegacyEnv` + `rewriteEnvWithDerivedTier`) so a future wizard "F-fix" path can reuse it. The user-facing warning (`MigrationReport.tierDerived` + `report.warnings`) names flags only — no `.env` value content. Explicit `SAFESPACE_TIER=` in source always wins.
- **`active-account` file copy** (H-NEW-2): also preserved across migration so the user's `account-switch` selection survives. Without this, post-migration the new dir had no `active-account` file and the user would get `null` active account on first proxy start.
- **No `--rollback` CLI**: sources are renamed to `safespace-{read,send}.migrated/` for manual `mv`-back, but no automated undo. Sec-rev C3 rationale: post-migration use of `safespace/` may mutate `last_used_at`; a "clean undo" is illusory once the new dir has been read. The user can revert by removing the new dir and renaming `.migrated/` back if they choose, accepting the risk of state drift.
- **All writes use `{mode: 0o600}`; all `mkdir` use `{mode: 0o700}`** (C2). Permission test asserts target dir + all 5 files (accounts.json, audit.jsonl, .env, audit-salt, optional salt-mismatch.warning marker).
- **`fs.rename` EXDEV** explicitly caught (L2): "single mount required" message.

### What the audit log still proves

The v1.x "procurement account physically can't send mail" structural defense is gone, but the **forensic record** is intact and unchanged:

- Every tool call appends `{ts, tool, account, argsHash, status, duration_ms}` to `audit.jsonl` (mode 0o600).

### Threat model addendum

The v2.0 redesign explicitly accepts these trade-offs:

- **A prompt-injected Claude at tier=write CAN send mail or share Drive files via any registered account.** Mitigations: (a) Claude Code's per-call approve UI surfaces the action before execution; (b) the user can choose `tier=read` to globally disable; (c) the audit log records every call for post-hoc review; (d) the user controls which accounts get registered at all.
- **A prompt-injected Claude at tier=share CAN create anyone-with-link Drive permissions.** Same mitigations. The shift from `tier=write` to `tier=share` is a deliberate user act (edit `.env` + restart) — it cannot be triggered by Claude.
- **The "register only what you're willing to expose" use-pattern is now a security invariant.** Documentation (README, wizard Step 3) names it explicitly so users with security mental models can act on it.

This is a meaningful weakening of one prior structural defense in exchange for substantial reduction in UX friction, plus explicit reliance on the Claude Code UI surface as a security boundary. For a single-user / private-repo / self-use deployment scope, the trade is intentional and well-tested.

## v2.1 Addendum — Drive share whitelist (2026-05-17)

Reintroduces a structural defense at the `drive_share_file` boundary: an opt-in, file-presence-toggled whitelist of folder + file IDs that defines what can be shared. `drive_unshare_file` bypasses the policy unconditionally — brakes always work.

This is **additive structural defense, not a v2.0 reversal**. v2.0 PR-2a (#56) removed `SAFESPACE_DRIVE_SHARE_ALLOWED_OWNERS` because it gated the wrong axis (file *owner*); this gates the right axis (file *location*). The two are not interchangeable.

### Why reintroduce structural defense at the share boundary

v2.0 traded the v1.x "two-profile structural defense" for tier-based `tools/list` filtering + Claude Code's per-call approve UI + the use-pattern "don't register high-risk accounts at tier=share". For a `share`-tier session with a registered account, **any** Drive file the account has access to is currently share-able. Two scenarios accumulate risk:

- **Prompt-injection of long-running agent sessions.** Background Claude Code sessions that process inbound mail / auto-archive / generate reports run at fixed tier with no human at the keyboard. The approve UI is only a guard while the user is watching. Whitelist is intent-independent: structurally, files outside the list cannot be shared.
- **Mixed-sensitivity Drive structures.** Most users have personal taxes, work strategy, and shareable client decks all in the same Drive. The v2.0 advice "don't register a high-risk account at share-tier" forces account-level segregation, which is heavyweight (separate consent, separate Keychain entry) for what is conceptually a folder-level distinction.

This addendum does not weaken any v2.0 mitigation. The `tools/list` filter, the per-call approve UI, the "don't register what you won't expose" use-pattern, the audit forensic line — all remain. Whitelist is an additional, opt-in structural layer at the tools/call boundary.

### Configuration: `drive-whitelist.json`

Schema v1 (lives at `${CLAUDE_PLUGIN_DATA}/safespace/drive-whitelist.json`, mode `0600`):

```json
{
  "schema_version": 1,
  "updated_at": "2026-05-17T10:23:45.000Z",
  "entries": [
    {
      "type": "folder",
      "id": "1aBcDeFgHiJkLmNoPqRsTuVwXyZ_01234567",
      "label": "Client A — shared with client",
      "added_at": "2026-05-17T10:23:45.000Z"
    },
    {
      "type": "file",
      "id": "1FileIdXyZ_0123456789abcdefGhIjKlMnOp",
      "label": "Recruiting deck (one-off)",
      "added_at": "2026-05-17T10:24:11.000Z"
    }
  ]
}
```

- `schema_version` enables future migrations.
- `type` is `"folder"` or `"file"`. Folder entries cover all descendants (subtree). File entries match exactly one file ID.
- `label` is for human readability only — never validated against Drive API at write time (a folder rename in Drive shouldn't break the policy).
- `added_at` is ISO 8601 UTC.
- Reader rejects unknown `type` values (fail-safe: deny the share rather than guess).

### Decision: default behavior — file-presence three-state

| State | Behavior | Rationale |
|---|---|---|
| **File absent** | Whitelist policy OFF — `drive_share_file` works as in v2.0 (tier gate only) | Backwards compatible. Users who haven't opted in are not surprised by `share_denied_by_policy` errors. Wizard prompts on first upgrade. |
| **File present, `entries: []`** | Default-deny — every share returns `share_denied_by_policy` | Explicit opt-in with zero entries = "I want default-deny but haven't added folders yet". Same semantic as `SAFESPACE_TIER=read` for the share path. |
| **File present, `entries: [...]`** | Whitelist enforced — only listed folder subtrees + file IDs share-able | The intended use mode. |

Rationale: a single boolean "whitelist on/off" requires either a second toggle or a magic sentinel value in the JSON. The file-presence design uses filesystem state directly and is auditable via `ls -la`.

### Decision: subtree inheritance for folder entries

A folder entry whitelists the folder and **all descendants, at any depth, via any parent chain**. Multi-parent files (Drive permits this) pass if **any** parent chain leads to a whitelisted folder (lenient OR — matches user expectation: "if it lives in this folder, it can be shared").

Drive shortcut files (`application/vnd.google-apps.shortcut`) resolve to their target file ID, and the target's parent chain is what's checked — not the shortcut's location. Rationale: a shortcut is a pointer, the security boundary lives at the target.

Max ancestor walk depth: **10**. Deeper trees deny + log. Prevents pathological API-cost behavior on folder cycles (which shouldn't exist in Drive but is defended against).

### Decision: `drive_unshare_file` unconditionally bypasses whitelist

Recovery > policy. If a misclick or prompt injection successfully creates a share on a whitelisted file, the user must be able to revoke it. Refusing `drive_unshare_file` on a non-whitelisted file would create a state where misconfigurations are unrecoverable.

Consistent with `drive_unshare_file` being exposed at every tier including `read`. The whitelist policy applies to **creation** of share permissions only.

### Decision: gate only `drive_share_file`, not `drive_get_file_content`

`drive_get_file_content` is already gated by Drive's own ACL — the proxy can only read what the account has been granted access to. A whitelist on read-path would add latency (mandatory parent walk on every fetch) without meaningful security gain. The read path stays untouched.

If a future use case emerges for read-side gating, it becomes a separate addendum with its own threat-model analysis. v2.1 scope explicitly defers it.

### Ancestor walk + LRU cache

For a `drive_share_file` call on `file_X`:

1. Check whitelist: is `file_X` directly listed (type=`file`)? → permit if yes.
2. Else walk parents via `gws drive files get fields:parents`. If `gws` returns shortcut metadata, resolve to target first. For each parent folder, check if it's in the whitelist (type=`folder`).
3. Recurse up to depth 10. Permit if any walked ancestor is whitelisted.
4. None match → `share_denied_by_policy`.

Caching:

- **Per-process LRU**: `Map<file_id, Set<ancestor_folder_id>>`, cap 1000 entries, TTL 10 minutes per entry.
- Cache populated on first walk. Cleared on MCP restart.
- Negative results (fully-resolved parent chain, not in whitelist) also cached.
- Whitelist file change → MCP restart required to pick up (consistent with `SAFESPACE_TIER` read-once-at-startup model).
- **Hit / miss counters exposed via `safespace doctor --json`** so TTL can be tuned with real data (Open Questions Q3 resolution: keep 10 min default, tune later if metrics show waste).

Cost model: cold call = N Drive API calls where N = ancestor depth (typically 1-3 for shallow trees, max 10). Subsequent calls on same file = 0 API calls.

### Error code: `share_denied_by_policy` (-32018)

PR-A spec proposed -32014; that code was already in use by `share_role_forbidden` (errors.ts:44). PR-B reassigns to -32018 (next free after -32017 `share_expiration_forbidden`). No semantic change — only the number.

```ts
{
  code: -32018,
  message: "Drive share denied by whitelist policy",
  data: {
    file_id: "<the file>",
    recovery: "Add the file's parent folder ID to drive-whitelist.json via /safespace-setup. Use `safespace doctor --json` to see the current whitelist.",
  },
}
```

The error does **not** leak which whitelist entries exist (no "your whitelist has X but you tried Y" hints). Same conservative tone as `tool_not_found` masking tier denials.

### Edge cases (spec-locked)

| Case | Behavior |
|---|---|
| File has 2+ parents, 1 whitelisted, 1 not | Permit (lenient OR) |
| Whitelist entry refers to deleted folder | `doctor` WARN at next run (Open Questions Q2 resolution: no separate staleness threshold — `doctor` catches it via 404 on real walks, not on a timer); share calls to other files still work |
| Drive returns 404 on parent walk | Deny + audit log entry; do not cache the failure (retry should be possible) |
| Shortcut file → resolve target before walking | Yes; whitelist applies to target's location |
| Whitelist JSON malformed | Fail-safe to "file present, entries: []" (default-deny). Stderr warning. `doctor` FAIL. |
| Whitelist file mode != 0600 | `doctor` WARN (matches `.env` mode check pattern) |
| Folder ID format invalid | Reject at write time (regex `^[A-Za-z0-9_-]{20,}$`), not at read time |
| API rate limit during parent walk | Return generic `share_denied_by_policy` (don't leak rate-limit state); audit log notes cause |

### Threat model addendum

What v2.1 defends:

- **Prompt-injection-induced over-sharing** (primary motivation). Adversarial content that convinces Claude to share sensitive files is structurally blocked when the file is outside the whitelist, regardless of what the approve UI shows.
- **Long-running agent over-share blast radius**. Background sessions cannot share beyond the explicit allowlist.
- **Misclicks in approve UI**. Two barriers instead of one.
- **Future `drive_share_folder`-like bulk tools**. Whitelist applies at the file/parent level; bulk operations inherit the gate.

What v2.1 does NOT defend:

- **Adversary with write access to `drive-whitelist.json`**. They can add anything. Mitigation: file mode `0600`, lives under `${CLAUDE_PLUGIN_DATA}/safespace/` (already mode 0700). If the adversary has filesystem write access at this level, the whitelist is the least of the problems.
- **Moving sensitive data into a whitelisted folder, then sharing**. SafeSpace doesn't observe Drive's internal `move` operations. Mitigation: keep whitelisted folders narrow + purposeful.
- **Sharing to wrong recipient within a whitelisted folder**. Whitelist gates WHAT, not WHO. A future recipient-allowlist (separate addendum) would address this.
- **Read-side over-exposure**. Out of scope per the read-path decision above.

### Migration (v1.1.0 → v1.2.0)

The wizard's Step 2 detection (introduced in #63) gets a new branch in PR-B: after handling the legacy-env trap, check for an existing `tier=share` user without `drive-whitelist.json`. Offer three choices:

1. **Set up whitelist now** — wizard interactive: paste folder IDs, validate format, write JSON.
2. **Skip — keep current open behavior** — no file written; v2.0 share-tier behavior preserved. `doctor` reports "whitelist not configured; tier=share fully open".
3. **Default-deny now, add entries later** — writes `{schema_version: 1, entries: []}`. Subsequent shares fail with helpful error until user adds entries.

Opt-in, not forced. Existing `tier=share` users do **not** start hitting `share_denied_by_policy` after the upgrade without explicit consent — same principle that v2.0's hard-fail decision tried to avoid (silent capability loss).

### Version: 1.2.0 (Open Questions Q4 resolution)

Minor bump. Feature is opt-in at file level — no automatic behavior change for users who don't engage with the wizard prompt. `2.0.0` is reserved for changes that flip behavior without consent (next breaking change candidate: OAuth flow refactor or `accounts.json` schema v3).

### Sec-rev pre-launch (PR-A coverage)

The whitelist module's pre-launch sec-rev focuses on:

- **File permission handling**: `drive-whitelist.json` atomic writes via `mktemp` → `rename(2)`; mode `0o600` preserved through write + rename.
- **Schema validation**: malformed JSON fails to "file present, entries: []" semantics (default-deny), never crashes the proxy; stderr warning is generic (no field-value echo).
- **Drive ID validation**: regex-anchored to known Drive ID shape (alphanumeric + `_` + `-`, ≥20 chars). Rejected at write time, not at read time.
- **LRU cache correctness**: TTL is per-entry; eviction follows LRU not FIFO; negative-cache entries cannot poison a later valid lookup (TTL expiry handles it).
- **Depth limit**: walk halts at 10 ancestors regardless of cache state. Cycles cannot cause unbounded API calls.
- **Audit log shape**: `share_denied_by_policy` event has no `target_email` or `share_type` fields (call rejected before those were validated). Canary test verifies.
- **Error message content**: no whitelist-state leakage; no file ID echo in stderr paths that hostile callers can trigger.

1. **Type gate**: `name` must be a string (not number / object).
2. **Trim + non-empty**: leading/trailing whitespace stripped before validation + send (mirrors Gmail web UI behavior); trimmed name must be non-empty.
3. **Header-injection rejection** on the raw name: CR / LF / NUL / NEL / U+2028 / U+2029 → reject. Runs against `args.name` directly (not the trimmed copy), so an input that's all-whitespace-plus-control would be caught here only if it didn't already trip gate 2's non-empty check — order doesn't change the security outcome (both gates reject), only the surfaced error message. Reuses the module-shared `HEADER_INJECTION_RE` (collapsed from a duplicated v1.4 PR-1 copy per sec-rev LOW-2 — single source of truth across `gmail_send` + `gmail_create_label`). Label name is not used in an RFC 2822 header path; this gate is defensive consistency, preventing prompt-injected names that smuggle line breaks into log views / Gmail UI.
4. **Byte-length cap**: ≤ 225 UTF-8 bytes after trim. Local fail-fast; the upstream limit is **not publicly documented** in Google's `users.labels.create` reference (sec-rev LOW-3), so the gate is advisory — error message acknowledges that upstream may also reject independently.
5. **System-label name blacklist** (case-insensitive on trimmed name):
   - Exact match set: `inbox`, `sent`, `unread`, `important`, `starred`, `draft`, `trash`, `spam`, `chat`.
   - Prefix block: `category_*` (covers Gmail's inbox categories — PERSONAL/SOCIAL/PROMOTIONS/FORUMS/UPDATES).
   - Reuses existing `system_label_forbidden` MCPError code. Echoed `name` in `errorData` capped at **first 64 chars** (sec-rev LOW-1) — bounds attacker-controlled bytes in the JSON-RPC error envelope.
6. **Visibility enum gate** (defense-in-depth against non-conforming MCP clients):
   - `label_list_visibility`: `labelShow` (default) | `labelShowIfUnread` | `labelHide`.
   - `message_list_visibility`: `show` (default) | `hide`.
7. **Idempotency — list-then-match before create**: calls `labels.list`, returns existing user-label resource on exact-name match (case-sensitive, mirroring Gmail's own semantic — Gmail allows distinct labels that differ only in case). TOCTOU between list and create is irrelevant: Gmail enforces name uniqueness server-side, so a race results in a 409 on the second creator, not a duplicate or boundary cross. Eliminates the "Claude is talked into creating 100 subtly-different duplicates" prompt-injection abuse class. Cost: one extra API call per create.

### What is intentionally NOT exposed in v1.4

- **`color`**: Gmail labels support `{textColor, backgroundColor}` from a fixed Google-defined palette. Out of scope for v1.4 — adds prompt-injection design surface (palette enforcement) without addressing a real user need. Users who want colors can micro-adjust via Gmail web UI after creation.
- **Nesting**: Gmail has no real label parent/child concept — `foo/bar` renders as nested in the UI but is one flat string. Schema description names this so Claude doesn't construct a "parent_id" param.
- **Label update / delete**: deferred. Update overlaps with `gmail_modify_message`-style write-with-confirmation surface; delete crosses into destructive recovery that the Gmail web UI handles cleanly.

### Audit

Standard `auditEnd` JSONL line (tool=`gmail_create_label`, account, args_hash, status, duration_ms) is sufficient. No `share_forensic`-style extra line — label create has no per-recipient blast radius and recording the raw label name would violate the "never record user content" invariant from `audit.ts`.

### Scope-excess note

`gmail.labels` also permits `labels.update`, `labels.delete`, `labels.patch` — neither registered in v1.4. Defense relies on the same pattern as v1.1/v1.2: (a) registry is the authoritative `requiredScopes` declaration, (b) the gws argv in `gmailCreateLabel` is a fixed literal (`["gmail", "users", "labels", "create", ...]`, not derived from user input). No handler-level argv-shape guard — same fragile-coupling reasoning as PR-3 L3.

### Tests

15 new unit tests in `src/tools/handlers.test.ts` covering: type gates, empty/whitespace, CR/LF/NUL/NEL/U+2028/U+2029 rejection, 225-byte cap (ASCII + multi-byte CJK regression-lock per v1.4 code-rev NIT), exactly-225 OK, 9 system-label names + case variants, CATEGORY_* prefix, visibility enum gates, default visibilities propagate into create body, idempotency hits list-only path, case-sensitive idempotency mismatch goes through create, trim before send, upstream 401 surface. 2 new registry tests (registry composition + min_tier=write). Suite: 472 pass (was 457).

## v2.2 Addendum — Recipient allowlist (2026-05-17)

Reintroduces structural defense at the third orthogonal axis: WHO can receive a share or send. v2.0 gave WHEN (tier), v2.1 added WHAT (Drive location). v2.2 adds WHO (recipient email/domain). The three axes compose — a successful exfiltration requires bypassing all three structurally, independent of Claude's intent.

This is NOT a return of v1.2's `SAFESPACE_DRIVE_SHARE_ALLOWED_OWNERS` (which gated file *owner* — the wrong axis, removed in v2.0 PR-2a #56). v2.2 gates the *recipient* — the right axis for "where the data goes".

### Why now (for personal use)

The personal-use threat model is dominated by two scenarios where the per-call approve UI is insufficient:

- **Background agent loops**: Claude Code session processing mail / auto-archiving / generating reports at fixed tier with no human at the keyboard. Approve UI is silent or auto-confirmed.
- **Prompt-injection across the WHO axis**: file is whitelisted (v2.1 OK), tier is share (v2.0 OK), but the prompt instructs Claude to share to `attacker@evil.com`. Without v2.2, the only defense is the operator catching the recipient in the approve UI — fragile for fast-moving sessions.

v2.2 makes "who receives data" a structural constraint, not an operator-attention constraint.

### Two-layer configuration (the design lock)

Recipients are inherently *session-volatile* (today's client is not tomorrow's) — unlike v2.1's *structurally stable* folder IDs. The storage choice reflects this: env vars, with a two-layer model parallel to `SAFESPACE_TIER`'s shell-overrides-`.env` semantics.

| Variable | Storage | Lifetime | Composition |
|---|---|---|---|
| `SAFESPACE_RECIPIENT_ALLOW` | `.env` (primary) or shell (replaces) | persistent / session | base set |
| `SAFESPACE_RECIPIENT_ALLOW_EXTRA` | shell only (additive; meaningless in `.env`) | session | added to base via union |
| accounts.json emails | filesystem | persistent | implicit self-send allow |

Effective allowlist at runtime:

```
allowed = parse(SAFESPACE_RECIPIENT_ALLOW) ∪ parse(SAFESPACE_RECIPIENT_ALLOW_EXTRA) ∪ accountsJsonEmails
```

The three sets are unioned once at proxy startup. Allowlist changes require Claude Code restart (same model as `SAFESPACE_TIER`, `drive-whitelist.json`).

### Tri-state truth table

| `SAFESPACE_RECIPIENT_ALLOW` state | Behavior |
|---|---|
| Unset entirely (no var in env) | Policy OFF — v2.0 behavior, no break for existing users |
| Set to empty string (`SAFESPACE_RECIPIENT_ALLOW=`) | Explicit default-deny — only self-send + EXTRA allowed |
| Set with entries | Enforced — only union members allowed |

Explicit empty-string vs unset distinction parallels v2.1's `drive-whitelist.json` file-absent vs `entries: []` distinction.

### Grammar: domain patterns + exact emails

Comma-separated values, leading/trailing whitespace tolerated:

```
SAFESPACE_RECIPIENT_ALLOW=@my-company.com, alice@client.com, @vendor-a.com
```

| Token | Meaning |
|---|---|
| `alice@client.com` | Exact match on recipient email |
| `@client.com` | Domain match — anyone at `client.com` |
| `client.com` (no leading `@`) | **Rejected at parse time** — must be unambiguous to avoid foot-gun |

Domain matching is case-insensitive on the domain part (RFC 5321 §2.4), case-sensitive on the localpart (most providers fold but RFC does not require; we don't, defense in depth).

### Tool scope (locked)

| Tool | Gated? | Fields checked |
|---|---|---|
| `drive_share_file` `share_type=user` | ✓ | `target_email` |
| `drive_share_file` `share_type=anyone` | (not applicable — no target_email) | — |
| `gmail_send` | ✓ | `to`, `cc`, `bcc` — all-or-nothing |
| `gmail_modify_message` | ✗ | label-only operation, no recipient |
| `gmail_create_label` (v1.4) | ✗ | label-only operation, no recipient |
| `drive_unshare_file` | ✗ | recovery > policy; brakes always work |
| Read tools | ✗ | no recipient surface |

### Check ordering inside `drive_share_file` (architectural fix from review)

v2.1 whitelist check walks parents via gws (up to 10 API calls per share). v2.2 check is in-memory Set lookup (microseconds). Wrong-recipient calls with valid file_id would otherwise pay v2.1's full API cost before getting rejected. Locked order:

```
1. Client-side validation (file_id regex, share_type, role, target_email, expiration_days)
2. Tier re-check (share_type=anyone → tier=share)
3. v2.2 recipient check          ← CHEAP, runs FIRST
4. v2.1 whitelist check          ← EXPENSIVE, only on recipient pass
5. gws permissions.create
6. audit share_forensic
```

For `gmail_send`, v2.2 is the only structural recipient gate (v2.1 doesn't apply to mail). Same client-side-then-policy order.

### Self-send implicit allow

Every email registered in `accounts.json` is implicitly allowed as a recipient — without this, the common "draft to self" pattern would require explicit listing. This is convenience-driven, but it IS a special case that operators can be confused by ("why did this share to my secondary account pass without being in ALLOW?").

**Doctor must explicitly show this layer**:

```
recipient_allow:        3 entries (1 domain, 2 emails)
recipient_allow_extra:  (none)
self_send_implicit:     4 emails from accounts.json
```

When `EXTRA` is set at shell level:

```
recipient_allow:        3 entries (1 domain, 2 emails)
recipient_allow_extra:  2 entries — session-only (1 domain, 1 email)
self_send_implicit:     4 emails from accounts.json
```

`safespace doctor --json` outputs the three counts as separate fields under `recipient_allowlist: { allow, extra, implicit_self }` for parseable inspection. Counts only — never the entries themselves (mirrors v2.1 "no leak of policy state" pattern).

### Error code: `recipient_denied_by_policy` (-32019)

```ts
{
  code: -32019,
  message: "Recipient denied by allowlist policy",
  data: {
    tool: "drive_share_file" | "gmail_send",
    rejected_count: <number>,
    total_recipients: <number>,
    recovery: "Add the recipient(s) to SAFESPACE_RECIPIENT_ALLOW in .env, or set SAFESPACE_RECIPIENT_ALLOW_EXTRA=<emails-or-domains> when launching Claude Code for a session-only grant. See README §Per-session recipient override.",
  },
}
```

**Spec invariant**: the error data does NOT include the rejected recipient values. Only counts. This mirrors v2.1's `share_denied_by_policy` "no leak of policy state" pattern. The audit log carries the hashed forensic detail (see below).

### Audit log: deny event shape

Parallels v1.2 `share_forensic` (success) and v2.1 `share_denied_by_policy` (whitelist deny). Recipients are hashed with the existing `audit-salt` HMAC-SHA256 — same key, same construction. This lets a log reader correlate "rejected attempts to send to X" with "successful sends to X" without ever storing recipient plaintext.

```json
{
  "ts": "2026-05-17T10:23:45.123Z",
  "tool": "drive_share_file",
  "account": "alice@example.com",
  "event": "recipient_denied_by_policy",
  "rejected_recipient_hashes": ["a3f8…64-hex…", "b7c9…64-hex…"],
  "rejected_count": 2,
  "total_recipients": 3,
  "duration_ms": 4
}
```

For `gmail_send`: `total_recipients = to.length + cc.length + bcc.length`. For `drive_share_file`: always 1.

**Field omissions**: no `file_id` (v2.2 may reject before reaching share-specific validation), no `share_type`, no `role`. The call was refused at the recipient gate; downstream-field intent was not validated.

### Wizard Step 2.6 (PR-B scope)

Only runs at `tier=write` or `tier=share` (the tiers where recipient-gate-able tools are exposed). Mirrors v2.1 Step 2.5's 3-way pattern:

> "SafeSpace v2.2 supports a recipient allowlist that gates `drive_share_file` and `gmail_send`. Without it, prompt-injection or long-running agent sessions could send/share to any recipient.
>
> **(S)et up allowlist** — type comma-separated domains (`@client.com`) or exact emails (`alice@client.com`). Wizard writes `SAFESPACE_RECIPIENT_ALLOW=...` into `$PLUGIN_DATA/safespace/.env`.
> **(K)eep open** — no var set; v2.0 behavior preserved. You can add later via re-running this wizard or editing `.env` directly.
> **(D)efault-deny** — wizard writes `SAFESPACE_RECIPIENT_ALLOW=` (empty). Only self-send + EXTRA allowed. Re-run wizard or edit `.env` to add entries."

Wizard does NOT write `SAFESPACE_RECIPIENT_ALLOW_EXTRA` to `.env` (defeats the per-session purpose). README explains the EXTRA shell-launch pattern at Step 6 success message.

### Threat model

What v2.2 defends:

- **Prompt-injection-induced over-share to wrong recipient**, agent or interactive: structurally blocked when the recipient is outside ALLOW ∪ EXTRA ∪ self.
- **Accidental cc-to-everyone**: same gate.
- **Compliance-hold "only legal@" mode**: `SAFESPACE_RECIPIENT_ALLOW=legal@own.com claude` for the session.
- **Long-running agent over-send blast radius**: recipients structurally bounded for the session.

What v2.2 does NOT defend:

- **Typos within allowlisted domain** (`alice → aliice` if both look valid). Domain match passes both. Mitigation: exact-email entries for high-value recipients.
- **Compromised insider at allowlisted org**: same allowlist, hostile recipient.
- **Reply-to header injection**: if `gmail_send` accepts a `reply_to` field, that's a separate output path. Verified in PR-B prep that current `gmail_send` does NOT accept `reply_to` — if added later, must be gated too.
- **Forwarding chains after legitimate send**: out of scope (Drive/Gmail-side; v2.2 controls what leaves the proxy).

### Architectural notes (locked from design review)

**Three orthogonal axes**: WHEN (tier) × WHAT (folder) × WHO (recipient). Each at a different policy boundary (tools/list / drive_share_file handler / drive_share_file + gmail_send handlers). Composable: an attacker must bypass all three.

**Storage asymmetry**: file (`drive-whitelist.json`) for v2.1, env vars for v2.0/v2.2. Reflects data volatility — folders are structurally stable, tier and recipients change per work session. NOT cosmetic inconsistency.

**Fourth-config-pattern flag**: with v2.2 the proxy has four distinct policy-config patterns (single env value for tier, comma-sep env list ×2 for recipients, JSON schema file for whitelist, plus the implicit tools/list-driven tier filter). Acceptable for v2.2; if v2.3+ adds another axis (time window, IP allowlist, payload size), consolidate to a unified `policies.json` schema. v2.2 explicitly defers consolidation.

> **v1.127 — the consolidation trigger fired, and consolidation is DEFERRED again (deliberately, with a reason).** `SAFESPACE_CONNECTORS` (`src/policy/connector-toggle.ts`) is exactly the "another axis" this flag anticipated: a WHICH-CONNECTOR axis alongside WHEN (tier) × WHAT (folder) × WHO (recipient). It does not trigger consolidation because it is the same config pattern as the tier — a single comma-separated env value read per request, filtering the same `tools/list` boundary — rather than a fifth one; and because it is the axis most likely to be set **per client config** (each client's `mcpServers` entry carries its own `env` block), which a shared `policies.json` file on the host would actively fight. Consolidation is still the right move the first time an axis needs *structured* config (nesting, per-operator overrides, or time windows); `SAFESPACE_CONNECTORS` needs none of those. Revisit if a per-operator `allowedConnectors` lands in `operators.json`.
>
> Note the axis composition rule: connector ∩ tier, narrowing-only. The connector axis can never carry a tool past its `min_tier` — proven by a subset assertion over all three tiers in `connector-toggle.test.ts`.

**Doctor verbosity**: v2.2 brings doctor's check count higher. Follow-up `safespace doctor --short` (issue-only filter) suggested as a tiny separate PR, not blocking v2.2.

Minor bump. Feature is opt-in at env-var level — no automatic behavior change for users who don't set `SAFESPACE_RECIPIENT_ALLOW`. `2.0.0` remains reserved for breaking changes (OAuth flow refactor, accounts.json schema v3).

### Sec-rev pre-launch (PR-A coverage)

The recipient-allowlist module's pre-launch sec-rev focuses on:

- **Domain matching correctness**: case-insensitive on domain (RFC 5321 §2.4), case-sensitive on localpart, no glob matching beyond `@domain.com` (no `*@*.foo.com` style — keeps the grammar simple + auditable).
- **Parse-time rejection of ambiguous tokens**: `client.com` (no `@`) rejected — must be `@client.com` (domain) or `localpart@client.com` (exact).
- **No content leakage**: error messages name fields and counts, never recipient values. doctor outputs counts + sources, never entries.
- **Audit hash invariant**: rejected recipients HMAC-SHA256 with the existing `audit-salt`. Canary test asserts plaintext recipient never appears in the audit line.
- **Self-send implicit-allow safety**: derived from `accounts.json` at module load, refreshed only on proxy restart (consistent with read-once policy). No way for an attacker to spoof `accounts.json` content (it's mode 0o600 + dir 0o700).
- **EXTRA-confusion DX**: README + doctor make ALLOW vs EXTRA distinction obvious. Test asserts EXTRA-set-in-.env behaves the same as EXTRA-set-in-shell (no semantic divergence).
- **Order of checks in handler**: recipient gate BEFORE whitelist gate (sec-rev review item #1). Test asserts a rejected recipient does not trigger any gws calls (mock fetcher must report zero calls).

## v1.10 Decision — Drive batch sharing deferred (2026-05-18)

Architecture decision (ADR-style): the v1.9.0 release-notes "Deferred / open follow-ups" entry for **Drive batch sharing** is hereby formally **deferred**. This addendum records the analysis so the question stops recurring at every release cycle.

### Context

v2.3 PR-C shipped `gmail_modify_messages_batch` with a ~300x throughput win (1000 labels: ~600s → ~1-2s). That tool sits on Gmail's `users.messages.batchModify` — a real server-side primitive that processes N message ids in one HTTP request, one transaction, one quota unit. The natural question: ship the same shape for Drive?

### Gmail vs Drive — the fundamental asymmetry

Drive's permissions API has **no `permissions.batchCreate` method**. The only batch-shaped mechanism is Google's generic HTTP batch endpoint (`/batch/drive/v3`), a multipart envelope the server unpacks into N independent `permissions.create` calls. Server-side they are processed individually — each consumes its own quota unit, each runs the full permission-creation transaction. So end-to-end latency is `N × per-permission processing + 1 × TLS RTT`, not `1 × API call` like Gmail.

### Quantitative ceiling (independent architect review)

Current measured per-call cost for `drive_share_file`:
- gws Python cold-start: ~600 ms
- Per-permission API processing: ~150-300 ms

With v2.3 PR-B's FIFO semaphore (`SAFESPACE_MAX_CONCURRENT_GWS=4`):

| N files | Sequential through semaphore | HTTP batch (bypass gws) |
|---|---|---|
| 20 | `ceil(20/4) × 900 ms ≈ 4.5 s` | `1 × 600 ms cold-start + 20 × 250 ms ≈ 5.6 s` |

**The HTTP batch path is *slower* than the existing semaphore-bounded sequential path** unless we also rewrite the gws subprocess layer as a native `googleapis` client — a major new code path that bypasses every argv-validated security gate. Speedup ceiling: negative.

### Options evaluated

| # | Approach | Speedup | Security cost | Verdict |
|---|---|---|---|---|
| A | **Defer (status quo)** — keep `drive_share_file` one-at-a-time; users iterate N tool calls under PR-B semaphore | Baseline (4.5 s for N=20) | None | **Selected** |
| B | New MCP tool `drive_share_files_batch`, sequential loop reusing per-file gates | Same as A (semaphore already amortizes) | Sec-rev cycle, partial-success semantics, audit cardinality decisions, batch cap | Speedup-free, surface cost real |
| C | New MCP tool, parallel HTTP `/batch/drive/v3` bypassing gws | **Negative** (~5.6 s for N=20) | New `googleapis` dep, bypasses gws argv validation, breaks "thin proxy over gws" design | Disqualified by quantitative analysis |
| D | Wait for gws upstream to add `permissions.batchCreate` | n/a | n/a | gws hasn't shipped batch in a year; unbounded |
| E | **`safespace share-batch` CLI subcommand** (not MCP tool) — shell-side loop over `drive_share_file` | Same as A | LLM blast-radius unchanged (no new tool exposure); operator opt-in via CLI flag | **Escape valve if demand materializes** |
| F | Anyone-only batch tool with `min_tier=share` + N ≤ 10 cap | Same as A | Sidesteps recipient-allowlist (no per-target gate); narrower than B | Less compelling than E (still adds MCP surface) |

### Decision: A, with E as the escape valve

Rationale:
1. **No speedup ceiling**: Drive's API doesn't support server-side batching; v2.3 PR-B's semaphore already amortizes gws cold-start across concurrent calls. There is no win to capture.
2. **Real security cost** for the loop-wrapper paths (B / F): partial-success semantics ("shared 3 of 5; what about the 2 that failed?"), audit-line cardinality decisions, recipient-allowlist all-or-nothing across multiple targets (raises unintentional whole-batch rejection probability), per-batch cap analogous to `MAX_MESSAGE_IDS_PER_BATCH=100`.
3. **No measured demand**: personal use rarely shares > 5 files per session. v2.3 PR-B + parallel `tool_use` blocks already make 5-file shares acceptable (~2-3 s combined).
4. **Option E preserves the escape valve**: if demand later materializes (open-source adoption, multi-file project workflows), ship a `safespace share-batch` CLI subcommand — operator-driven, no LLM blast-radius increase, reuses the same per-file 7-layer defense. Cheaper than any new MCP tool by far.

### Non-decision: surface symmetry

The asymmetric design between Gmail (has batch) and Drive (no batch) is **intentional**. SafeSpace follows the underlying API capabilities, not surface symmetry. `gmail_modify_messages_batch` exists because `messages.batchModify` is a real server-side primitive; Drive permissions has no equivalent, so we do not invent one.

### Revisit triggers

Pull this decision and design a batch tool only if:
1. **gws upstream ships `permissions.batchCreate`** support, OR Google's REST API gains a true server-side batch method (i.e., the API surface changes underneath us).
2. **Measured bulk-share demand**: > 10 files shared per session, > 3 sessions per week sustained over a month. Ship Option E (CLI subcommand) first; only design Option B (MCP tool) if the CLI path proves insufficient for ergonomic reasons.
3. **A 4th security axis is added** to the threat model — that's a v2.4 architectural fork that should rationalize all batch tools together.

### Where this leaves the deferred-items table

After this addendum, the v1.9.0 release-notes entry "Drive batch sharing" is **closed-deferred** (decision recorded, no work pending). The remaining open items in that table (`policies.json` consolidation, `SAFESPACE_MAX_CONCURRENT_GWS` real-world calibration) are unaffected.

> **Supersession note (added 2026-05-18 in v1.11 ADR below)**: this decision was made under the gws-subprocess constraint. If the v1.11 migration to direct googleapis ships, Drive batch becomes ~9x faster (semaphore-bottleneck removed) and worth revisiting. Track as a post-v1.11 follow-up.

### v1.11 post-update re-evaluation (2026-05-19, issue #101)

After v1.11 Phase 4 closed, issue #101 reopened the Drive batch question per the supersession note above. **The original Decision A (defer) still holds, but the reasoning is updated**: the supersession note's "~9x faster" claim compared pre-v1.11 sequential gws to post-v1.11 HTTP batch. Under post-v1.11 numbers, the correct comparison is **parallel SDK calls vs HTTP batch**, and **parallel SDK wins decisively** (21.5x at N=50). A `drive_share_files_batch` MCP tool built on the HTTP batch endpoint would be a major performance regression vs the LLM's existing ability to issue N parallel `drive_share_file` tool_use blocks in one turn.

#### Original 3 revisit triggers — none satisfied

1. **Google API gains server-side batch** → ❌ Drive REST still has no `permissions.batchCreate`; only the generic `/batch/drive/v3` multipart envelope, which (per Google's own docs and the measurements below) processes sub-requests server-side **sequentially**.
2. **Measured bulk-share demand > 10 files/session × 3 sessions/week × 1 month** → ❌ No such measurement exists. Personal-use pattern unchanged from v1.10.
3. **4th security axis added to threat model** → ❌

#### Measured numbers (`scripts/bench-drive-batch.ts`, 2026-05-19)

Real `drive.permissions.create` calls against a live Drive account from Taiwan (Asia), recipient = self-bench plus-address (`sendNotificationEmail: false`). One run per N; latency is wall-clock from first call to last response.

| N | Sequential (`for await`) | Parallel SDK (`Promise.all`) | HTTP batch (`/batch/drive/v3`) |
|---|---|---|---|
| 10 | 24,138 ms | **3,149 ms** (7.7x vs seq) | 6,658 ms (3.6x vs seq) |
| 20 | 32,933 ms | **2,030 ms** (16.2x vs seq) | 11,603 ms (2.8x vs seq) |
| 50 | 79,465 ms | **2,614 ms** (30.4x vs seq) | 56,113 ms (1.4x vs seq) |

**Scale behavior is the key finding**: Parallel SDK total time is **~flat in N** (TCP connection pool saturates, total time ≈ slowest single request). HTTP batch is **linear in N** (Google processes sub-requests server-side sequentially — confirms the "not necessarily processed in parallel" warning in Google's batch docs).

| Parallel SDK relative speedup vs HTTP batch | N=10 | N=20 | N=50 |
|---|---|---|---|
| | 2.1x faster | 5.7x faster | **21.5x faster** |

The gap widens with N. At N=50, HTTP batch is barely 1.42x faster than sequential one-at-a-time; the multipart envelope's server-side serialization eats most of the savings from the single wire round-trip.

#### Updated conclusion

**Decision A (defer) reaffirmed** with a stronger reason:

1. **Speedup ceiling has flipped sign vs the original analysis** — in v1.10's Option C (gws cold-start dominant), HTTP batch was *slower* than the gws-semaphore-bounded sequential path. Now that gws is gone, **parallel SDK is *also* faster than HTTP batch** — by a large factor that grows with N.
2. **LLM-driven parallelism is the right surface**: a Claude turn can already include N parallel `drive_share_file` tool_use blocks. The proxy has no semaphore (Phase 4 removed it); each call goes straight to `drive.permissions.create`. The user-facing capability "share 50 files at once" is **~2.6 s wall-clock** at no new code cost. Shipping a `drive_share_files_batch` tool would *worsen* this by 21x.
3. **Option E (`safespace share-batch` CLI) escape valve still stands** — for operator workflows that can't use Claude turns (e.g., scripted bulk shares), a CLI subcommand that issues `Promise.all` of N `drive.permissions.create` calls is the right shape; it does NOT need the HTTP batch endpoint. Defer the CLI subcommand until measured demand triggers it (criterion #2 above).
4. **Triggers 1 + 3 unchanged**.

#### What this means for code

- **Issue #101: close, no work pending.** Decision recorded; numbers documented; bench script committed for future re-validation.
- **`drive_share_file` (single) is sufficient.** Phase 3 PR-5 (#99) ships the correct surface; no Phase 5 batch follow-up.
- **`src/google-api/batch.ts` stays Gmail-only.** Generalizing it to Drive would only be valuable if `permissions.batchCreate` were added upstream.

#### Bench script reproducibility

`scripts/bench-drive-batch.ts` is the measurement source-of-truth. Re-run if (a) Google changes Drive batch behavior, (b) the user's location relative to Drive data centers changes (the absolute numbers will shift; the *ratio* should remain ~constant), (c) v2.x architectural change reopens the question.

## v1.11 Decision — Migrate from gws subprocess to direct googleapis (2026-05-18)

The largest architectural shift since v2.0 (single-profile collapse) and the second since Step 5 A0 (gws subprocess pivot). This ADR records the decision to **fully migrate** SafeSpace's Google API access from the `gws` Python subprocess to direct `googleapis` (Node) calls, the 5-phase plan, and the forcing functions to prevent perpetual hybrid drift.

**Status (2026-05-19)**: **COMPLETE**. All 5 phases shipped. Issue #92 closed. Python no longer a SafeSpace runtime dependency. See phase table below for PR list; Drive batch follow-up issue opened post-Phase-4.

**Supersedes**: Step 5 §A0 "Architecture pivot: gws subprocess (replaces Approach B-lite / C)". The gws pivot was correct under the constraints of 6 months ago (Step 0 spike, ~400 LoC budget, ship-fast-and-don't-reinvent-OAuth thesis). Those constraints no longer bind.

### Why now — the three forcing observations

**1. Argv-contract bug class is structural, not bad luck.**

The proxy currently serializes typed TS objects → positional argv → URL query / JSON body → gws Python argparse → gws's own re-typing → Google REST. Six conversions, zero compile-time contract. Four production bugs in three PRs within the v1.8.0 → v1.10.0 cycle have hit this layer:

| PR | Tool | Bug |
|---|---|---|
| #71 | `gmail_create_label` | shipped with `--body` flag; gws 0.22.5 rejects with `validationError` |
| #46 | `gmail_modify_message` | same `--body` bug |
| #77 | both above | both fixed to `--json` |
| #82 | `gmail_send` | `raw` shipped via `--params` (URL query) instead of `--json` (request body) — URL length limit + Gmail rejects unknown query param |

All four bugs were caught by *spikes*, not by tests — fake-`gwsExec` mocks meant the contract never surfaced in CI. Argv-shape capture tests added in PRs #77 and #82 lock yesterday's shape but cannot anticipate the next gws minor deprecation. `googleapis` npm types collapse all six conversions into one TS call site that fails `tsc`, not prod. **Treatment: remove the layer.**

**2. Performance is now a primary axis, not a secondary one.**

| Metric | gws path (current) | Direct googleapis | Factor |
|---|---|---|---|
| Per-call latency (cold) | ~600 ms Python cold-start + ~250 ms API = **~850 ms** | ~50 ms first TLS + ~5-10 ms subsequent | **~85x** |
| 5 parallel tool_use blocks per turn | 4 served + 1 queued = ~4.5 s (semaphore cap=4) | 5 × ~10 ms in parallel = ~50 ms | **~90x turn latency** |
| Peak RSS | 4 × ~100 MB Python = **~400 MB** | ~50 MB Bun proxy | **~8x lower** |
| Drive download cap | `DRIVE_MAX_BYTES = 5 MB` (per-tool, drive_get_file_content); `MAX_BODY_BYTES = 10 MB` default + `MAX_BODY_BYTES_HARD_CAP = 50 MB` absolute ceiling on `gwsExec` — must buffer | unlimited via `ReadableStream` | **enables new capability** |
| Concurrent calls bound | `SAFESPACE_MAX_CONCURRENT_GWS=4` | Google quota (~1000+/s in practice) | **effectively unbounded** |

The ~90x turn-latency improvement is the user-facing difference between "wait" and "instant" for an LLM workflow that fires 5 parallel tool calls per turn.

**3. The dual-architecture pattern is already empirically validated by kaidashi.**

`kaidashi` is a separate private Python project (a personal CLI, not in this repo) that **already calls Google APIs directly** for Gmail + Drive (1164 LoC across `google_auth.py` / `gmail_api.py` / `drive_api.py`), and **already piggybacks SafeSpace's stored OAuth credentials** read-only (Keychain `service=safespace-mcp` + `.env` under SafeSpace's configDir). kaidashi closes the largest unknowns:

- Direct googleapis works at production scale for a similar surface
- Auth-sharing between a long-lived MCP proxy and a separate consumer process is empirically a working pattern
- HTTP batch endpoints (`/batch/gmail/v1`) are accessible via `googleapis` Python client's callback pattern — confirms the same shape is available in `googleapis` npm

### What was considered and rejected

| Option | Why rejected |
|---|---|
| **Stay on gws + add argv-shape tests** | argv-shape capture tests lock yesterday's shape; the next gws minor deprecation re-fires the same bug class. Treats a symptom, not the cause. |
| **Hybrid per-tool (architect's original recommendation: ship 1 first)** | Perpetual hybrid trap: dual mocking pattern, dual testing burden, dual documentation, every new tool requires a "which path?" decision. Hybrid endpoint is not a stable architecture; it's a frozen migration state. Performance ceiling stays on half the tools forever. |
| **Direct HTTP via `google-auth-library` + raw `fetch` (no `googleapis` SDK)** | Reserved as **Plan B** if Phase 1a spike fails. ~80% of the wins for ~5% of the SDK surface, but loses TypeScript types on response shapes (re-introduces a weaker version of the argv contract problem). |

### What the gws "process boundary as defense" was, and why it doesn't hold

Earlier analysis weighted the gws-subprocess boundary as defense-in-depth: if SafeSpace's sanitize had a bug, gws was a separate process that couldn't be persuaded to do something with user data. Architect review (2026-05-18) refuted this:

- The threat model is **LLM-driven prompt-injection of tool arguments**, not gws compromise
- The OAuth access token is **already in the proxy's env** (`GOOGLE_WORKSPACE_CLI_TOKEN`) and handed to gws — if the proxy is compromised, it already has the token
- sanitize, audit, argv-construction, and the MCP stdio loop **all run in-proc** today; the OS process boundary buys nothing against the actual adversary
- What gws *does* give us is **a separately-maintained HTTP client** (SDLC argument, not runtime isolation); `googleapis` npm has the same property with a larger user base

The defense gws actually provides is **already supplied by `googleapis` npm under the same SDLC argument**.

### Phase ordering — why `drive_get_file_content` is LAST, not first

An earlier draft of this plan ordered `drive_get_file_content` first in Phase 2 to maximize perf demo value. Architect review (2026-05-18, second pass) inverted this:

- Sanitize-wrap boundary moves: streaming changes from "buffer to `Uint8Array` then sanitize" to "accumulate chunks with per-chunk cap then sanitize on full assembly." Sanitize MUST run AFTER full assembly (it scans for adversarial sequences across the whole text).
- The current binding security gates on Drive downloads are `DRIVE_MAX_BYTES = 5 MB` (per `drive_get_file_content`, per DESIGN.md §P1(c)) and `MAX_BODY_BYTES_HARD_CAP = 50 MB` (absolute ceiling on `gwsExec`). Streaming removes both; the replacement is a per-chunk accumulator with early-abort cap. That mechanism must be designed in isolation, not bundled with "first ever direct-API call."
- handlers.ts (`drive_get_file_content` pre-flight) has an explicit TOCTOU note saying the pre-flight is advisory and the `gwsExec` cap is the binding gate. Migrating without first establishing where the new binding gate lives creates a window where the binding gate doesn't exist.

`gmail_list_labels` is the right first migration: smallest JSON response, no sanitize complexity, exercises auth + error mapping end-to-end in the cleanest possible shape.

### Forcing functions to prevent perpetual hybrid

"3-5 weeks" is optimism, not a forcing function. The argv-contract layer kept producing related-but-distinct bugs across releases: v2.3 PR-C fixed `--body` on label/modify, then v1.10 surfaced a different sub-class (`--params {raw}` on `gmail_send`) only weeks later — same family, different shape. Bug classes survive "we'll fix it" cycles. Concrete failure mode: Phase 3 sec-rev blocker, codebase sits in hybrid state for 2 release cycles, gws-path bugs get patched in-place, now we have two argv-contract bug classes coexisting with a googleapis path.

Forcing functions (pick **at least two**, applied at Phase 1b merge):

| Function | Strength | Cost |
|---|---|---|
| `gwsExec` deprecation log per call (annoying-by-design stderr noise) | Strongest | Trivial (~5 LoC) |
| `setup.sh` pins gws version + refuses upgrades | Strong (stops bug-fix-in-place temptation cold) | Trivial |
| CI check failing if a PR touches `gwsExec` after `<date>` | Medium (forces conversation) | ~10 LoC + commit-hook |
| Implicit "we'll finish" | Weakest (current) | 0 |

Decision: apply the **first two** at Phase 1b merge. The CI date-bomb is optional and depends on Phase 2 velocity.

### kaidashi piggyback amendment (refresh_token rotation race)

Today: SafeSpace's `refresh.ts` has a per-account `Map<email, Promise>` mutex; gws subprocess reads Keychain fresh on every spawn (~600 ms latency window before kaidashi sees a stale token). kaidashi explicitly does NOT write back to Keychain — relies on SafeSpace to be authoritative.

Post-migration, SafeSpace becomes long-lived in-process with `refresh.ts` as authoritative cache. The window where kaidashi sees a token SafeSpace already invalidated (because SafeSpace wrote a NEW refresh_token via Google's rotation) widens from "next gws spawn" to "proxy uptime."

`refresh.ts` already flags this risk (line 11-14: "Two Claude Code instances refreshing the same email in parallel will race; v1 accepts last-writer-wins"). Post-v1.11, kaidashi becomes that second "instance" in practice.

**Mitigation (must land in Phase 1b)**: SafeSpace's refresh path always **re-reads Keychain for `refresh_token` before POSTing the refresh request**. Don't trust the in-process TokenSet cache for the refresh_token field — always Keychain-read it. Access token in-process cache is fine (short-lived, easy to detect 401). refresh_token rotation is rare in Google's actual behavior (most refreshes return the same refresh_token), but the cost of being wrong is "kaidashi sees `invalid_grant` and the operator has to re-consent" — high-friction, easy to avoid.

Pre-check: grep SafeSpace + kaidashi + private notes for any other Keychain `service=safespace-mcp` consumer before Phase 1 ships. If there is one, this ADR's piggyback contract must extend to cover it.

### Test infrastructure shift

The current ~500 LoC of fake-gws shell-script fixtures across handlers.test.ts + neighbours simulates:

| Scenario | gws relevance | Direct API relevance |
|---|---|---|
| Argv corruption (`--params` vs `--json` mapping) | Yes — the bug class | **Obsolete by design** (good) |
| Exit-code + stdout coupling | gws-specific contract | Obsolete |
| Subprocess kill/timeout/SIGKILL escalation | gws path | **Maps to**: gaxios request hang past timeout, HTTP/2 RST_STREAM, hung TCP without timeout |
| OS pipe buffer backpressure | gws path | **Maps to**: gzip truncation, response stream backpressure |
| Partial-write on SIGKILL | gws path | **Maps to**: TLS reset mid-stream |

(1)-(2) are obsolete by design. (3)-(5) map to transport-layer concerns under googleapis. Mocking `mock.module('googleapis')` mocks the SDK layer, NOT the transport. To preserve adversarial parity, Phase 1b's transport-level mocks must use **fetch/undici-level interceptors** (msw, undici interceptors, or a fetch shim) — different mocking style, more code. The "+60-80 tests" estimate for Phase 1b accounts for this; the earlier "+30 tests" undercounted.

Concrete lost-without-replacement scenario: a test where gws hangs for 35s and SIGTERM/SIGKILL escalation fires maps to "gaxios request hangs past `timeout`." If only mocked at `googleapis` level, this can't be simulated. Transport mocks are non-optional in Phase 1b.

### Bun + googleapis compatibility — Plan B is real

`googleapis` is ~50 MB unpacked with deep Node-ism surface: `child_process` for ADC fallback, `fs` for credential files, `http2` for HTTP/2 batch. Bun has documented gaps in `http2`, `worker_threads`, and `tls`. Most likely landmine: `googleapis`' streaming codepath under Bun surfaces a quiet bug on files > some threshold or under concurrent connection reuse — i.e., exactly the `drive_get_file_content` streaming case.

Phase 1a spike must validate at minimum:
1. `gmail.users.labels.list` — auth + JSON response baseline
2. `gmail.users.messages.send` with a 1 MB body + attachment — write-path baseline
3. `drive.files.get` metadata-only — Drive baseline
4. `drive.files.get` with `alt=media` for a 50 MB file as a stream — the riskiest path

If any of (4) fails (segfault, hang, missing Node API, silent truncation), **swap to Plan B** before Phase 1b: `google-auth-library` + raw `fetch` calls. Plan B captures ~80% of the wins (no argv layer, no Python cold-start, type safety on request bodies via in-tree types) with ~5% of the SDK footprint. Response types become hand-written interfaces (regression: a weak version of the argv contract problem). Acceptable as a fallback; not the preferred path.
